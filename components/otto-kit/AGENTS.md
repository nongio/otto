# otto-kit

The crate every Otto app is built on, and the one the compositor draws its own chrome with: a Wayland client runtime, a Skia drawing layer, a widget set and a design system. Apps take the runtime (`AppRunner`, `AppContext`, surfaces, protocols); the compositor calls only the drawing half (`WindowDecoration`, `WindowControl`, `ContextMenuRenderer`, `theme`, `typography`, `icons`).

How it works: [otto-kit](../../docs/developer/otto-kit.md).

- **Layer:** toolkit. Used by the compositor, every kit crate (`otto-md-kit`, `otto-media-kit`, `otto-auth-ui`, `otto-peek`, `otto-agents-kit`) and every toolkit app.

## Dependencies
- **Internal:** `otto-foundations` (re-exported as `otto_kit::xdg`, `otto_kit::uri`, `otto_kit::matching`) and `otto-dbus` (the `org.otto.*` proxies, re-exported as `otto_kit::dbus`).
- **External:** `smithay-client-toolkit` and `wayland-client`; `skia-safe` (gl, textlayout, svg, skottie), re-exported as `otto_kit::skia`; `laye-rs` for the retained scene graph; EGL, loaded at run time. From the compositor it needs `zwlr_layer_shell_v1`, `ext_session_lock_v1`, fractional scale, `zwp_text_input_v3`, pointer gestures and Otto's own protocols. It follows the `org.freedesktop.portal.Settings` portal for colour scheme, accent and locale, puts up file dialogs through the portal's `FileChooser`, and serves accessibility through AccessKit over AT-SPI. The `dictation` feature adds PipeWire capture and an HTTP speech-to-text client.

## Develop
- `cargo build -p otto-kit`; `cargo run -p otto-kit --example simple_app`. `examples/` (one per component or surface pattern) is the practical reference.
- Against a dev compositor: `cargo run -- --winit &`, then `WAYLAND_DISPLAY=wayland-1 cargo run -p otto-kit --example form_controls_gallery`.
- `RUST_LOG` through `logging::init`. `OTTO_COLOR_SCHEME` (light/dark fallback), `OTTO_SOLAR_ICONS` (the glyph set) and `OTTO_KIT_BACKDROP=effect|none` change what an app draws.
- Tests: `cargo test -p otto-kit`. Each icon-theme test in `tests/` is its own binary on purpose: the icon lookup reads the XDG directories once. `cargo bench -p otto-kit --bench pane_paint` measures pane painting.
- The `testing` feature exposes `otto_kit::testing::TestClient`, the SHM-only client the compositor's `headless` tests drive.

## Where things are
- The runtime: `src/app_runner/` (the `App` trait, `AppRunner`, `AppContext`) and `src/surfaces/` (one type per Wayland role).
- Drawing: `src/rendering/` (EGL, Skia, the lay-rs renderer) and `src/components/` (the widget set).
- The design system: `theme.rs`, `typography.rs`, `icons.rs`, with the portal watchers sharing `portal_settings.rs`.
- `portal_file_chooser.rs` is the one `org.freedesktop.portal.FileChooser` client: apps build a `Request` and `spawn` it rather than calling the portal themselves.
- The desktop wallpaper's layout, frame rendering and drawing are `src/wallpaper/`, shared by the compositor and the settings app's preview; `src/utils/resample.rs` is the high-quality CPU resampler it renders with.
- Otto's own protocols are generated in `src/protocols/`; desktop entries, file types, previews, clipboard, drag and drop, sound and Lottie have their own modules.

## Rules
- Anything in `src/components/` draws from a bare `&Canvas`: no connection, no event loop, no surface. An interactive component takes a state struct the caller owns and hands events to; it never subscribes to anything itself.
- `WindowDecoration`, `WindowControl` and `ContextMenuRenderer` are drawn by the compositor too, so a change lands on server-side decorations and the dock's menus as well.
- `src/protocols/` is generated by `wayland_scanner` from the XML in the repository's `protocols/`. Change the XML, not the bindings.
- User-facing strings go through `t!`, keyed in `resources/locales/en-GB.ftl`, the one catalogue that carries every key. See `src/i18n/mod.rs`.
- `AppContext::enable_layer_engine` runs before the first surface is created.
- Other crates reach Skia through `otto_kit::skia` rather than adding `skia-safe` themselves.
